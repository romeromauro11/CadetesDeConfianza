01

ShoppingOnline

Marketplace local pensado para que cualquier emprendedor o comercio pueda tener su propia tienda online, sin depender solo de redes sociales.

Qué es

Plataforma de comercio electrónico local donde cada comercio abre su propia tienda dentro de un marketplace unificado.

Problema que resuelve

Muchos comercios chicos venden de forma desordenada por redes sociales, sin catálogo, stock ni presencia digital propia.

Público objetivo

Emprendedores y comercios locales como vendedores; compradores de la zona. El sitio opera por localidad: cada ciudad tiene su propio marketplace dentro de la misma plataforma.

Estado del proyecto

En producción

Objetivo del sistema: darle a cada comercio una tienda propia, con su catálogo, precios y stock, dentro de un marketplace que organiza todo por categoría y localidad para que el comprador encuentre rápido lo que busca cerca suyo.

02

Arquitectura

Vista general de cómo se conectan el frontend, el backend, la base de datos y los servicios externos.

La decisión de arquitectura más importante del proyecto: no todo pasa por un backend propio. La mayoría de las lecturas y escrituras van directo del navegador a Supabase (PostgreSQL + Auth), protegidas por Row Level Security a nivel de fila en la base — no por lógica de servidor. Un backend propio en Node solo existe para lo poco que necesita un secreto de servidor o un límite de velocidad real: pagos, alta de administradores, formularios públicos y firma de subida de imágenes.

Cliente

Frontend estático

HTML/CSS/JS vanilla — marketplace, panel de vendedor y admin

Datos

Supabase (Postgres + Auth)

El frontend le habla directo. La seguridad la da Row Level Security, no un backend en el medio

Servidor

API propia (Node/Express)

Solo lo que necesita un secreto o rate-limiting: pagos, admins, formularios públicos

Edge

Cloudflare Worker

SEO por tienda (meta tags, JSON-LD), sitemap dinámico y headers de seguridad

Archivos

Cloudinary

Subida de imágenes firmada desde el navegador, sin pasar por el servidor

Externos

Mercado Pago · Resend

Cobro de planes y campañas · emails transaccionales

Frontend

Sitio estático sin framework: marketplace público, panel del vendedor y panel de administración como tres apps separadas que comparten el mismo cliente de Supabase.

Supabase (Postgres + RLS)

El frontend inserta y consulta filas directo, con la clave pública ("anon key"). Esa clave está pensada para ser pública; lo que autoriza o bloquea cada operación son las políticas de RLS en la base.

API propia

Node/Express desplegado en Render. Existe solo para lo que RLS no puede resolver por sí solo: usar una clave secreta de servidor, o limitar cuántas veces alguien puede escribir por hora.

Cloudflare Worker

Además de servir los archivos estáticos, intercepta cada request: si es la URL de una tienda, busca sus datos en Supabase e inyecta metaetiquetas y JSON-LD antes de responder, para que los buscadores indexen cada tienda sin migrar a un framework con SSR.

Cloudinary

El navegador sube la imagen directo a Cloudinary con una firma de un solo uso que emite la API. El servidor nunca recibe el archivo — solo autoriza la subida y aplica los límites del plan antes de firmar.

Servicios externos

Mercado Pago para el cobro de planes y campañas de publicidad (con verificación de firma del webhook), y Resend para los emails transaccionales (cartilla aprobada/rechazada, plan por vencer).

Base de datos

Modelo relacional en PostgreSQL. Estas son las tablas principales y cómo se relacionan entre sí.

Cadena de identidad y catálogo

auth.users emprendedores tiendas productos producto_imagenes

Cadena de ubicación (define qué tiendas ve cada visitante)

provincias localidades tiendas tienda_localidades

Otras relaciones relevantes: tiendas ↔ categorías (muchos a muchos) · tiendas → planes · campañas → paquetes de publicidad → localidades · cada acción de moderación queda registrada con su admin, tienda y denuncia asociada

tiendas

El nodo central del modelo

CREATE TABLE public.tiendas (
  id             integer PRIMARY KEY DEFAULT nextval('tiendas_id_seq'),
  emprendedor_id uuid REFERENCES emprendedores(id),
  localidad_id   integer REFERENCES localidades(id),
  nombre         character varying NOT NULL,
  slug           character varying UNIQUE
                 CHECK (slug_valido(slug::text)),
  plan_id        integer REFERENCES planes(id),
  estado         character varying NOT NULL DEFAULT 'pendiente'
                 CHECK (estado IN ('borrador','pendiente','aprobada','rechazada')),
  revisado_por   uuid REFERENCES admins(id),
  deleted_at     timestamptz
  -- + verificada, destacada, rating, whatsapp, multi_localidad_activo...
);
Relación: pertenece a un emprendedor, a una localidad y a un plan. De acá cuelgan productos, fotos, secciones, campañas y reseñas. El estado con CHECK evita que una fila quede en un estado que no existe.

productos

Producto publicado dentro de una tienda

CREATE TABLE public.productos (
  id            integer PRIMARY KEY DEFAULT nextval('productos_id_seq'),
  tienda_id     integer NOT NULL REFERENCES tiendas(id),
  categoria_id  integer REFERENCES tienda_secciones(id),
  nombre        character varying,
  precio        numeric,
  precio_oferta numeric,
  oferta_hasta  date,
  stock         integer DEFAULT 1,
  visible       boolean DEFAULT true,
  disponible    boolean DEFAULT true,
  deleted_at    timestamptz
);
Relación: pertenece a una tienda y a una sección propia de esa tienda (no a la categoría general del marketplace — son dos árboles distintos a propósito). deleted_at en vez de un DELETE real: borrado lógico.

localidades

Cada ciudad tiene su propio marketplace

CREATE TABLE public.localidades (
  id                        integer PRIMARY KEY DEFAULT nextval('localidades_id_seq'),
  provincia_id              integer NOT NULL REFERENCES provincias(id),
  nombre                    character varying NOT NULL,
  activa                    boolean DEFAULT true,
  cantidad_minima           integer DEFAULT 15,
  multiplicador_publicidad  numeric NOT NULL DEFAULT 1
                            CHECK (multiplicador_publicidad > 0),
  fecha_habilitacion        timestamptz
);
Relación: agrupa tiendas de una provincia. cantidad_minima es el piso de tiendas para habilitarla; multiplicador_publicidad hace que anunciar en una ciudad grande cueste más que en un pueblo chico.

planes

El modelo de negocio, como filas de una tabla

CREATE TABLE public.planes (
  id                      integer PRIMARY KEY DEFAULT nextval('planes_id_seq'),
  slug                    character varying UNIQUE NOT NULL,
  precio_mensual          numeric NOT NULL DEFAULT 0,
  max_fotos               integer NOT NULL DEFAULT 3,
  max_productos           integer NOT NULL DEFAULT 0,
  con_panel               boolean DEFAULT false,
  destacado               boolean DEFAULT false,
  estadisticas_avanzadas  boolean DEFAULT false
);
Relación: cada tienda referencia un plan (y opcionalmente un plan_pendiente_id mientras se procesa un cambio). Los límites de fotos, productos y funciones salen de acá, no están escritos a mano en el código.

campanias

Publicidad paga, con cupo por localidad

CREATE TABLE public.campanias (
  id          integer PRIMARY KEY DEFAULT nextval('campanias_id_seq'),
  tienda_id   integer REFERENCES tiendas(id),
  paquete_id  integer NOT NULL REFERENCES paquetes_publicidad(id),
  estado      character varying NOT NULL DEFAULT 'pendiente_pago'
              CHECK (estado IN ('borrador','pendiente_pago','en_revision',
                             'activa','pausada','rechazada','finalizada')),
  mp_payment_id text,
  inicio      date,
  fin         date
);
Relación: una campaña elige un paquete (tipo de anuncio + duración + precio) y una o varias localidades vía campania_localidades. El estado modela todo el flujo: desde borrador hasta pagada y aprobada por un admin.

moderacion_logs

Auditoría: quién hizo qué

CREATE TABLE public.moderacion_logs (
  id            integer PRIMARY KEY DEFAULT nextval('moderacion_logs_id_seq'),
  admin_id      uuid NOT NULL REFERENCES admins(id),
  accion        character varying NOT NULL CHECK (accion IN (
                'tienda_aprobada','tienda_rechazada','tienda_desactivada',
                'denuncia_revisada','emprendedor_bloqueado' /* ... */)),
  tienda_id     integer REFERENCES tiendas(id),
  denuncia_id   integer REFERENCES denuncias(id),
  detalle       text
);
Relación: cada acción de un admin (aprobar, rechazar, bloquear) queda registrada con quién la hizo y sobre qué tienda o denuncia. No se puede editar un catálogo del panel de admin sin dejar rastro.

08

Decisiones técnicas

Decisiones concretas tomadas durante el desarrollo, y por qué se tomaron.

Problema

Un backend propio manejando cada lectura y escritura era un salto de red innecesario para operaciones simples, y una superficie de ataque más grande de mantener.

Decisión

Mover la mayoría del CRUD a Supabase directo desde el frontend, protegido por Row Level Security. El backend Node quedó solo para lo que necesita un secreto de servidor o rate-limiting real.

Motivo

Menos capas para lo simple, y un backend enfocado únicamente en lo sensible: pagos, alta de admins, formularios públicos, firma de imágenes.

Resultado

Backend más chico y fácil de auditar. La seguridad vive en un solo lugar: las políticas de RLS.

Problema

Cada vendedor pegaba la URL de su propia cuenta de Cloudinary para las fotos: fricción de alta y cero moderación real sobre lo publicado.

Decisión

Centralizar en una sola cuenta de Cloudinary del proyecto, con subida firmada desde el navegador — el servidor solo emite la firma, nunca recibe el archivo.

Motivo

Onboarding sin fricción y control real: las imágenes viven en una carpeta por tienda, nadie puede reemplazarlas después de aprobadas.

Resultado

Subida en un clic, con los límites de cada plan aplicados antes de firmar, no después.

Problema

El sitio es una SPA sin framework con SSR — cada tienda necesitaba su propia página indexable, con metaetiquetas y datos estructurados propios.

Decisión

Resolver el SEO en el edge: un Cloudflare Worker intercepta la request, busca los datos de la tienda en Supabase e inyecta el <head> antes de responder.

Motivo

Evitar una reescritura completa del frontend solo para tener SEO por tienda.

Resultado

Cada tienda se indexa individualmente, con OpenGraph y JSON-LD, sin cambiar de stack.

Problema

Los IDs de pago de Mercado Pago no son secretos: cualquiera podía golpear el webhook con un ID real y forzar una confirmación de pago falsa.

Decisión

Verificar la firma HMAC-SHA256 de cada notificación, con comparación de tiempo constante, y no procesar nada si el secreto no está configurado (fail-closed).

Motivo

Un webhook sin verificar es, en la práctica, un endpoint público para extender el vencimiento de un plan sin pagar.

Resultado

Solo Mercado Pago puede disparar una confirmación real; una config faltante bloquea en vez de dejar pasar.

09

Problemas y soluciones

Situaciones reales encontradas durante el desarrollo y cómo se resolvieron.

Seguridad de pagos

El webhook de Mercado Pago podía dispararse sin haber pagado

Problema

Los IDs de pago de Mercado Pago no son secretos. Cualquiera podía golpear el webhook con un ID real y forzar que se confirmara un pago inexistente, estirando el vencimiento de un plan sin pagar de nuevo.

Análisis

No había ninguna verificación de que la notificación viniera realmente de Mercado Pago — se confiaba en el contenido del request sin más.

Solución

Verificación de la firma HMAC-SHA256 del header de la notificación con comparación de tiempo constante, y fail-closed: sin el secreto configurado, no se procesa nada.

Resultado

Solo notificaciones legítimas de Mercado Pago pueden confirmar un pago.

Bug de cobro

Las campañas en varias localidades se cobraban como si fueran una sola

Problema

El precio de una campaña de publicidad se tomaba directo del precio base del paquete, sin importar cuántas localidades había elegido el anunciante.

Análisis

El precio real depende de la cantidad de localidades y del multiplicador propio de cada una — esa cuenta vivía en una función de la base, pero el checkout no la estaba usando.

Solución

El checkout pasó a calcular el monto con la misma función de base de datos que ya usaba el panel de administración para mostrar y simular precios.

Resultado

Una campaña de varias localidades cobra lo que corresponde, con una sola fuente de verdad para el precio.

Seguridad de emails

El nombre de una tienda podía inyectar HTML en un email transaccional

Problema

El nombre de la tienda y el motivo de un rechazo — texto cargado por el emprendedor o un admin — se insertaban tal cual en el HTML de los emails de aviso.

Análisis

Un nombre de tienda con markup podía terminar inyectando contenido o links en un email enviado desde el dominio de confianza del proyecto.

Solución

Todo texto cargado por usuarios se escapa antes de insertarse en el HTML del email, con el mismo criterio que ya se usaba en el frontend.

Resultado

El contenido cargado por usuarios nunca vuelve a interpretarse como HTML.

Bug de infraestructura

El tracking fallaba en silencio según con o sin "www" entrara el visitante

Problema

El sitio responde tanto con "www" como sin él, pero la variable de entorno con la URL del frontend solo podía tener un valor. Quien entraba por la variante no configurada tenía el tracking de eventos roto por CORS, sin ningún error visible.

Análisis

El CORS del backend comparaba contra un único origen — la otra variante del dominio quedaba, sin querer, fuera de la lista permitida.

Solución

Generar automáticamente ambas variantes (con y sin "www") a partir de la URL configurada, en vez de depender de que alguien cargue las dos a mano.

Resultado

Tracking consistente sin importar por qué variante del dominio entre el visitante.

Bug de datos

Borrar un moderador podía dejar huérfana la tienda de un emprendedor

Problema

Dar de baja a un admin borraba también su cuenta de autenticación. El alta de admins reutiliza cuentas existentes, así que alguien que era admin y emprendedor a la vez perdía su cuenta entera al sacarle el rol.

Análisis

El endpoint de borrado no distinguía si esa cuenta también tenía una fila en emprendedores antes de eliminarla de Auth.

Solución

Antes de borrar la cuenta de autenticación, se comprueba si también es emprendedor; si lo es, solo se quita el rol de admin y la cuenta se conserva.

Resultado

Sacar a alguien del equipo de moderación ya no rompe la tienda de nadie.

Debugging

Cambiar la localidad de una tienda desde el panel no hacía nada — sin ningún error

Problema

Desde el panel de administración, editar la localidad de una tienda parecía no tener efecto: no aparecía ningún error, pero el valor quedaba exactamente igual después de guardar.

Análisis

La tabla tiene un trigger que protege campos sensibles (plan, verificación, localidad, entre otros) de ediciones no autorizadas, y solo deja pasar el cambio si la sesión pertenece a un admin real. Las primeras pruebas se habían hecho directo en el editor SQL de la base, donde no existe una sesión de usuario — ese contexto nunca cuenta como admin, así que el trigger revertía el cambio en silencio.

Solución

En vez de tocar el trigger (que cumple una función real de seguridad), se confirmó el comportamiento probando desde una sesión de admin real dentro del panel, donde la identidad sí se resuelve correctamente.

Resultado

El mecanismo de protección sigue funcionando como corresponde, y quedó documentado que el editor SQL directo no es un lugar válido para probar cambios que dependen de la identidad de quien los hace.

Bug de producto

"Sumar al carrito" aparecía aunque la tienda no tuviera WhatsApp cargado

Problema

El carrito de consulta arma un pedido y lo manda por WhatsApp al número de la tienda — pero el botón para sumar productos se mostraba siempre, sin importar si la tienda tenía un número cargado o no.

Análisis

Para una tienda sin WhatsApp, el link final del carrito quedaba armado sin destinatario, roto en silencio. El comprador podía terminar armando una lista entera de productos sin ninguna forma real de enviarla.

Solución

El botón de sumar al carrito, y el ícono del carrito flotante, ahora dependen de que la tienda tenga WhatsApp cargado — si no lo tiene, directamente no se ofrece esa opción.

Resultado

Ya no existe ese callejón sin salida: si el carrito está disponible, siempre hay un canal real para enviarlo.

Bug de catálogo

Una sección de productos podía quedar completamente afuera de la carga inicial de la tienda

Problema

La carga inicial de una tienda trae hasta 60 productos, pero se tomaban como un bloque global ordenado por orden sin distinguir secciones. Una sección cuyos productos arrancaban con un orden alto podía quedar completamente afuera de esos primeros 60, aunque sus productos existieran y estuvieran bien vinculados a ella.

Análisis

El filtro para mostrar una sección puntual comparaba nombres de texto en vez del id real de tienda_secciones — frágil ante mayúsculas o espacios. Además, la función tenía el offset de la carga general fijado en cero ("Ver más" nunca avanzaba) y devolvía el total topado en 60, ocultando que había más productos y convirtiendo el límite real del plan en un límite de 60. Se confirmó todo pidiendo la definición exacta ya desplegada en la base y probándola en vivo antes de tocar nada.

Solución

Se reescribió la función para repartir la carga inicial en round-robin real entre secciones, respetando el offset real en las páginas siguientes, se cambió el filtro de sección para usar su id numérico en vez del nombre, y se sumó paginación propia de a 20 dentro de cada sección.

Resultado

Todas las secciones aparecen desde que se abre la tienda sin importar su orden interno, "Ver más" funciona tanto en la vista general como adentro de una sección, y el límite real del plan sigue siendo el techo — nunca la estrategia de carga inicial.

Bug de subida de imágenes

Ningún logo ni foto de galería se podía subir: Cloudinary rechazaba la firma

Problema

De un día para el otro, subir el logo o las fotos de la tienda durante el onboarding empezó a fallar siempre: Cloudinary devolvía 401 Invalid Signature y la imagen nunca llegaba a existir del lado de Cloudinary.

Análisis

El endpoint de firma armaba la firma incluyendo max_file_size junto con folder y timestamp, pensado para que Cloudinary rechazara del lado del servidor cualquier archivo mayor a 8MB. El problema: max_file_size no es un parámetro real de una subida firmada manual — solo existe como ajuste de un "Upload Preset" configurado en el panel de Cloudinary. Cloudinary lo ignoraba por completo al reconstruir su propia firma esperada, así que la firma calculada acá nunca podía coincidir, sin importar que las credenciales estuvieran perfectas. Antes de llegar ahí se descartaron por evidencia otras hipótesis más obvias — credenciales rotadas en Render, caché de un deploy viejo — comparando directamente el string to sign que reportaba el error de Cloudinary contra lo que el código realmente firmaba.

Solución

Se sacó max_file_size de lo firmado (y de lo que manda el navegador), dejando la firma solo con lo que Cloudinary realmente valida. El límite de 8MB se mantiene igual, pero chequeado del lado del navegador antes de subir — que era, en la práctica, la protección real que existía desde el principio.

Resultado

Las subidas de logo, banner, galería y fotos de producto volvieron a funcionar al toque. Queda pendiente, como mejora futura, mover ese límite a un Upload Preset propio si algún día hace falta que Cloudinary también lo rechace por su cuenta.

Evolución

Cómo fue creciendo el proyecto versión a versión.

V1 — Versión inicial

Todo pasaba por el backend

Un backend Node/Express clásico manejaba login, alta de tiendas y productos, localidades y moderación — cada operación, sin importar cuán simple, cruzaba por el servidor.

V2

Migración a Supabase + RLS

La mayoría de las lecturas y escrituras se movieron a Supabase directo desde el frontend, protegidas por Row Level Security. El backend Node quedó reducido a lo que necesita secretos de servidor: pagos y alta de administradores.

V3

Publicidad, SEO y hardening

Subida de imágenes firmada a Cloudinary, sistema de publicidad y campañas con Mercado Pago, notificaciones transaccionales por email, un Cloudflare Worker para SEO en el edge, y una ronda de seguridad: CSP, webhook fail-closed, saneo de HTML en emails, CORS con y sin "www".

Estado actual

Marketplace en producción operando por localidad, con panel de vendedor completo (catálogo en tarjetas o planilla tipo Excel, secciones propias, QR imprimible) y panel de administración con moderación, campañas y analítica.

Próximos cambios

Roadmap

El foco hoy está puesto en hacer crecer el marketplace: sumar más tiendas, afinar la estrategia de marketing y la presencia en redes sociales, y el trabajo constante de encontrar y resolver bugs en producción. Del lado del código, estoy evaluando mejoras al panel de vendedor para simplificar la carga de productos — hoy es, para mí, la parte más pesada de esa experiencia.
